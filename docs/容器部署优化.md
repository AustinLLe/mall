# 松果集市 容器部署优化

> 项目名称：松果集市  
> 文档版本：v2.5 
> 更新日期：2026-08-26  
> 范围：现有 Docker Compose 单体部署；操作入口统一为启动面板。不实施微服务拆分。

---

## 1. 两套用法，不要混

| | 日常开发（已有） | Docker 部署（本次补齐） |
|--|--|--|
| 入口 | `NewSecondMall-启动面板.cmd` 第 1、3、4、8 项 | **同一面板新增一项：构建并启动 Docker** |
| 后端 | `mvnw spring-boot:run`，本机 **8080** | `mvn package` → 镜像内 JAR，**不映射 8080** |
| 前端 | HBuilderX CLI **`launch web`**，本机 **5173** | HBuilderX CLI **`publish h5`** → Nginx 静态站 |
| 数据库 | 本机 MySQL（面板第 8 项） | Compose 里的 `mysql:8.4` |
| 浏览器 | `http://localhost:5173`，接口打本机 8080 | 只开 **`http://localhost`（或 `.env` 的端口）** |

开发继续用 1 + 3；交作业、演示容器、按「线上同构」起栈，用 Docker 那一项。不要一边 `spring-boot:run` 一边再 compose 映射 8080。

HBuilderX **可以**自动化（本机 `cli.exe`），**不能**进 Linux 镜像编译。因此镜像仍是运行时：宿主先打 JAR 和 H5，再 `compose up --build`。面板负责把这几步收成一次选择。

## 2. 目标形态

操作者双击 `NewSecondMall-启动面板.cmd`，选 **「构建并启动 Docker」** 后，脚本自动：

1. 检查 Docker、`deploy/.env`、HBuilderX CLI。
2. 后端：`shopping_back/shopping_back` 下 `mvnw -DskipTests package`，确认 `target/shopping_back-*.jar`。
3. 前端：`cli publish --platform h5 --project <shopping_front 绝对路径>`；若产物在 `web/`，处理成 Dockerfile 能 COPY 的目录（见阶段 B）。
4. `docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build`。
5. 提示打开 `PUBLIC_ORIGIN`（默认 `http://localhost`）。

日常开发菜单保留。Docker 项失败时打印缺什么（没 Docker / 没 `.env` / 没找到 `cli.exe` / JAR 或 `index.html` 不存在），不要只丢 compose 日志。

运行时拓扑不变：

```
启动面板「构建并启动 Docker」
  ├─ mvn package  → JAR
  └─ cli publish  → unpackage/dist/build/h5 或 web
        ↓
deploy/.env（密码、PUBLIC_ORIGIN、端口）
        ↓
docker compose up --build
        ↓
mysql:8.4  →  backend(JRE+JAR, :8080 仅内网)  →  nginx(:80 对外)
```

| 容器 | 作用 | 对外 |
|------|------|------|
| `mysql` | `shop_db`，空卷首次执行 `doc/db.sql` | 否 |
| `backend` | Spring Boot 单体 | 否 |
| `frontend` | Nginx：H5 + 反代 `/api/` `/files/` `/ws/` | 是，`${HTTP_PORT:-80}` |

浏览器只访问 Nginx。密钥只进 `deploy/.env`，不进镜像。

## 3. 现状差距

| 问题 | 影响 |
|------|------|
| 面板只有开发启动，没有 Docker | 部署仍要手打 JAR、点发行、再 compose |
| `frontend.Dockerfile` 写死 `h5/` | 新版 HBuilderX 常出 `web/`，镜像构建失败 |
| 无产物校验 | 缺 JAR / 缺 `index.html` 时失败难读 |
| `PUBLIC_ORIGIN` 说明弱 | 和地址栏不一致会被 CORS 拦住 |
| `db.sql` 只在空卷执行一次 | 改表不会随 compose 自动迁移 |
| Nginx `proxy_pass` 写死 `http://backend:8080` | 前缀已分开，但拆服务要改三处；详见阶段 E |
| 后端探活绑 `/api/products` | 单体可用；拆服务后可能失效；详见阶段 F |

已正确、必须保持：密码走 `.env`；backend 不映射 8080；Nginx 按 `/api/` `/files/` `/ws/` 分前缀。

面板已具备：扫描 `HBuilderX.exe` / `cli.exe`（`HBUILDERX_EXE`、`HBUILDERX_CLI_EXE`）、`launch web`、`launch mp-weixin`。Docker 项 **复用找 CLI 逻辑**，命令从 `launch` 换成 `publish`。

---

## 4. 优化目标（本次）

1. 启动面板增加 **构建并启动 Docker**，一条路径完成 JAR + 发行 H5 + compose。
2. 修好 H5 COPY 路径（`h5` / `web`），面板构建后 compose 能反复成功。
3. 配置只走环境变量；一个对外入口；Nginx 具名 upstream（为以后拆服务留口）。
4. 写清 Nginx 现状与改法、后端探活为何绑 `/api/products`（本次单体可继续用，拆服务再换）。
5. 文档以面板为准，不再把「手动 mvn + 菜单发行 + 手打 compose」当主流程。

不做：迁 uni-cli、Linux 镜像内编前端、K8s、拆 JAR、本次不改探活路径。

## 5. 执行方案

### 阶段 A：面板接入 Docker（已实施）

**已改** `NewSecondMall-LaunchPanel.ps1`（`NewSecondMall-启动面板.cmd` 不用改）。

菜单：

```
9.  构建并启动 Docker（改代码后用：打包 + 发行 + 启动）
10. 停止容器
11. 查看容器状态
12. 删除容器数据库（需 YES，不自动启动）
13. 重新启动容器（不重新打包）
```

第 3 项仍是开发预览：`launch web` → `localhost:5173`。第 9 项是 **发行静态文件进容器**。

**9 的实际步骤**

1. 无 `cli.exe`：提示设 `HBUILDERX_CLI_EXE`。
2. 无 `docker` / 不支持 `docker compose`：提示安装 Docker Desktop。
3. 无 `deploy/.env` 时从 `.env.example` 复制。密码或 `PUBLIC_ORIGIN` 为空 / 仍是 `replace-with-...` 时，**当场询问** Docker 容器的库用户名和密码（默认用户 `shop_user`；root 密码回车则与应用密码相同），写入 `.env` 后继续，不再报错退出。这是容器内新建库的口令，不是本机 MySQL root。
4. `shopping_back\shopping_back` 下 `mvnw.cmd -DskipTests package`，确认 `target\shopping_back-*.jar`。
5. `cli publish --platform h5 --project <shopping_front 绝对路径>`；失败则再试 `publish web`。**等发行结束**再 compose。
6. 探测 `h5\index.html` / `web\index.html`（都有则取较新的），写入 `.env` 的 `H5_DIST_DIR`。
7. 在 `deploy/` 执行 `docker compose --env-file .env -f docker-compose.yml up -d --build`。
8. 打印容器状态（`docker compose ps`）并尝试打开 `PUBLIC_ORIGIN`。返回菜单后可用第 11 项再次查看。

第 10 项：`docker compose stop`。只把容器停下，**库还在**。之后用第 13 项启动。

第 11 项：`docker ps -a`（过滤 `deploy-`），不刷日志。

第 12 项：删除容器数据库（输入 YES）。Docker 无法在容器占用卷时删库，因此内部是 `down -v`：拆掉容器并删除 `mysql_data` / `upload_data`。**不会自动再启动**。本机 Windows MySQL 不受影响。

第 13 项：重新启动。先 `compose start`，若容器已被拆掉则 `up -d`（不 `--build`，不打 JAR、不发行 H5）。删库后要用空库跑起来：12 → 13。改了前后端代码要用第 9 项。

compose 失败时不再误报「H5 COPY / CORS」，改为打印容器状态和 backend 日志。

**首次**：选第 9 项时按提示输入即可；脚本会写 `deploy/.env`。以后若 `.env` 里已有非占位密码，不再询问。

| 变量 | 含义 |
|------|------|
| `MYSQL_ROOT_PASSWORD` | 容器内 MySQL root |
| `DB_USERNAME` | 应用库用户，默认 `shop_user` |
| `DB_PASSWORD` | 应用用户密码 |
| `PUBLIC_ORIGIN` | 浏览器地址栏源，如 `http://localhost`；端口非 80 则 `http://localhost:8088` |
| `HTTP_PORT` | 宿主机映射 Nginx 的端口，默认 80 |
| `AI_BARGAIN_API_KEY` / `DASH_SCOPE_API_KEY` | 可选 |

`deploy/.env` 已 gitignore，不得提交。

**验收 A**

- 未预先手动发行 H5、未手打 `mvn package` 时，只选第 9 项能起三个容器。
- 首页、登录、`/api/`、`/files/`、`/ws/` 可用。
- 第 1、3 项行为不变。

**常见失败（面板应能对应提示）**

| 现象 | 原因 | 处理 |
|------|------|------|
| 找不到 cli | 未装 HBuilderX 或路径未扫到 | `HBUILDERX_CLI_EXE` |
| frontend COPY 失败 | 产物在 `web/` | 阶段 B + 脚本同步目录 |
| 找不到 jar | package 失败 | 看 Maven 输出 |
| CORS | `PUBLIC_ORIGIN` 与地址栏不一致 | 改 `.env` 后重新 up backend |
| 库空 / 缺表 | 旧卷，init 只跑过一次 | 第 12 项 `down -v` 后再 9 |
| backend Restarting / Access denied | `.env` 密码与 mysql 数据卷不一致 | 第 12 项删库，再第 13 项启动 |
| 80 占用 | 本机 Nginx/IIS | `HTTP_PORT=8088` 且 `PUBLIC_ORIGIN` 带端口 |

### 阶段 B：前端 COPY 路径（已实施）

`deploy/frontend.Dockerfile` 用构建参数，不再写死 `h5/`：

```dockerfile
ARG H5_DIST_DIR=shopping_front/unpackage/dist/build/h5
COPY ${H5_DIST_DIR}/ /usr/share/nginx/html/
```

`docker-compose.yml` 的 `frontend.build.args` 读取 `.env` 的 `H5_DIST_DIR`，缺省仍是 `h5/`。

`.env.example` 已增加：

```text
# HBuilderX 发行目录（相对仓库根目录）。新版常为 web，旧版为 h5。
H5_DIST_DIR=shopping_front/unpackage/dist/build/h5
```

构建前确认该目录存在 `index.html`。新版 HBuilderX 发行到 `web/` 时，把 `.env` 改成：

```text
H5_DIST_DIR=shopping_front/unpackage/dist/build/web
```

阶段 A 的面板会在 `publish` 后自动探测 `h5`/`web` 并写入或传入该变量。在此之前需手动改 `.env` 或保证目录与 `H5_DIST_DIR` 一致。

**验收**：仅有 `build/web/` 且 `H5_DIST_DIR=.../web` 时，`docker compose build frontend` 成功，容器内 `/usr/share/nginx/html/index.html` 存在。

### 阶段 C：配置只进环境变量（已实施）

保持：Dockerfile 无密码/域名；compose `environment:` 注入；不要把 `.env` COPY 进镜像。

已补：

- `docker-compose.yml` 的 MySQL `MYSQL_USER` 与 backend `DB_USERNAME` 均读 `${DB_USERNAME:-shop_user}`，密码仍只来自 `.env`。
- `.env.example` 增加 `DB_USERNAME=shop_user`，并注明本地 Docker 的 `PUBLIC_ORIGIN=http://localhost`（`HTTP_PORT` 不是 80 时必须带端口）。

禁止：Dockerfile 写死 `DB_PASSWORD`；把真实密钥提交进 `application.properties`。

### 阶段 D：一个对外入口（已核对）

compose 只映射 frontend 的 `${HTTP_PORT:-80}`。backend / mysql 无 `ports:`。课设看库用 `docker compose exec`。

`docker-compose.yml` 的 frontend 端口处已加注释：不要给 backend / mysql 增加 ports。

容器内 H5 继续请求相对路径 `/api`、`/ws`、`/files`，不要写 `http://backend:8080`。

面板第 1 项仍连本机库、本机 8080，与 Docker 栈分开。

---

### 阶段 E：Nginx 具名 upstream（已实施）

浏览器只打到 **frontend 容器的 80**。Nginx 按 URL 前缀分流。

| 路径 | 作用 | upstream |
|------|------|----------|
| `/` | H5 静态页 | 本机 `try_files` |
| `/api/` | REST | `upstream_api` → `backend:8080` |
| `/files/` | 上传文件 | `upstream_files` → `backend:8080` |
| `/ws/` | 聊天 WebSocket（带 Upgrade） | `upstream_ws` → `backend:8080` |

`deploy/nginx/default.conf` 顶部：

```nginx
upstream upstream_api     { server backend:8080; }
upstream upstream_files   { server backend:8080; }
upstream upstream_ws      { server backend:8080; }
```

`proxy_pass` 使用 `http://upstream_api` 等形式，**不要带尾斜杠**，以便把 `/api/products` 原样转到后端。三个 upstream 目前仍指向同一个 `backend`，用户无感知。拆微服务时只改顶部 `server` 行，例如：

```nginx
upstream upstream_api   { server shop:8080; }
upstream upstream_files { server shop:8080; }
upstream upstream_ws    { server chat:8080; }
```

不要改成「整个站点一个 `location /` 反代到 backend」。

**验收**：改完后聊天、上传、商品列表与改前行为一致。需重新 `compose up --build` frontend（或面板第 9 项）后才生效。

---

### 阶段 F：后端探活（`/api/products`）

Docker 会定期问 backend 容器「你还活着吗」。只有 healthy 之后，frontend 才会启动（compose 里 `frontend.depends_on.backend.condition: service_healthy`）。

探活写在 `deploy/backend.Dockerfile`：

```dockerfile
HEALTHCHECK --interval=15s --timeout=5s --start-period=30s --retries=5 \
  CMD wget -q -O - http://127.0.0.1:8080/api/products >/dev/null || exit 1
```

含义：每隔 15 秒在容器内部 GET 商品列表；能返回就当健康，否则 unhealthy。选 `/api/products` 是因为它现在一定存在、且不需要登录，顺便证明「进程起来了 + Tomcat 在听 + 这条业务接口通」。

**当前单体可以继续用。** 局限是探活绑死了一条业务 API，不是通用健康检查：库挂了或商品接口挂了，容器也会被判不健康（有时这是好事）。以后若拆成 auth / shop / chat 多个服务，auth 容器可能根本没有 `/api/products`，探活会一直失败，frontend 永远等不到 healthy。

拆服务时再改成 Spring Boot Actuator 的 `/actuator/health`，或各服务自己的探活路径。本次优化 **不改探活命令**，只把耦合记下来，避免评审时当成必须立刻修的缺陷。
